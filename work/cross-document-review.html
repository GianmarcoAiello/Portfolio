Case study /02 — in production

CROSS-DOCUMENT
COMPLIANCE
REVIEW

A public-sector healthcare compliance programme: each project requires a multi-document compliance checklist reviewed by domain professionals. The engine applies 52 rules and returns an auditable outcome per rule — the final verdict is always computed by code.

RoleLed design & delivery
ContextPublic-sector healthcare
StatusIn production
Scale52 rules · 8 attachment types
01Context

Professionals read every project document by hand and filled in checklists — sampling, not exhaustive; roughly 2 hours of shallow checks per project. Sampling meant real compliance risk stayed unread. An earlier pilot had failed: unclarified exceptions accumulated in the tool and the experts lost trust in it.

02Approach

Process first, technology second. Before development: an exception inventory and co-design with the domain experts. Then an agentic pipeline over project document folders — intake (OCR, classification into attachment types, prompt-injection scan), rule catalogue, execution, guardrails, aggregation. The operator keeps the same working method and the same output file; what changes is who does the reading.

  • Rule catalogue generated from the operators' own instructions, reviewed by a person, versioned — no retraining when instructions change.
  • ~1/3 of the rules are deterministic (no model): cheap, identical on every run.
  • Evidence-based judgement: an OK requires a verifiable quote from the source; low confidence or missing grounding becomes "to verify", never a silent pass.
  • Full traceability: per-rule detail plus a timestamped event log — audit-ready.
FIG.02 — five stages per project folder. Gray fill = deterministic code, red tint = the stage where the model judges, plain = external system. Dashed = return path to the operator.
03Results
  • ~2 hours of manual checks per project → 5–15 minutes, with exhaustive coverage instead of sampling.
  • The control is stricter than the manual one it replaced — not just faster.
Lesson
Process first, technology second. The earlier pilot failed because unclarified exceptions accumulated in the tool and experts lost trust. After the exception inventory and co-design with domain experts — before development — trust in the output became a project metric, not an assumption.
